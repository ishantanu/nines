# Nines

Manage service level objectives and critical user journeys as code.

Nines connects reliability goals to the user journeys they protect. Define SLOs and journey links in versioned YAML, measure them with Prometheus or Mimir, and inspect SLI, error budget and burn-rate history in a web workspace. Use the CLI offline for validation and rule generation, or connect it to a tenant-scoped server for review and apply.

[Measurement-quality checks](https://ishantanu.github.io/nines/docs/measurement-quality/) explain freshness, population counts and cohort failures. [Error-budget response policies](https://ishantanu.github.io/nines/docs/error-budget-policy/) connect that evidence to owner review and deterministic CI gates. Native providers are currently Prometheus and Mimir; see [provider extension boundaries](https://ishantanu.github.io/nines/docs/provider-adapters/).

[SLI menus and templates](https://ishantanu.github.io/nines/docs/slo-templates/) provide experimental starting points for services, pipelines, storage, agents, LLM applications and inference. Generate editable YAML offline with `nines templates generate`, or choose a template in the portal. [AI workload guidance](https://ishantanu.github.io/nines/docs/agent-slos/) explains outcome evaluation, budgets and conditional latency measurements.

[SLO extensions](https://ishantanu.github.io/nines/docs/slo-extensions/) let teams publish declarative measurement recipes, typed inputs, policy presets and evaluation contracts independently. Install bundles from local files, HTTPS artifacts or commit-pinned Git repositories. Installed bundles are pinned by version and digest; rendering produces ordinary SLO YAML without runtime code execution.

[The optional AI workload playground](https://ishantanu.github.io/nines/docs/deployment/ai-playground/) exercises agent tasks, evaluation quality and coverage, budgets and inference histograms through real Prometheus/Mimir recording rules. It is synthetic and requires no model account.

**Status: pre-release MVP, under active development.** Expect regular features and fixes as the platform develops. APIs use `nines.dev/v1alpha1` and may change before a stable release. Use the MVP for evaluation and early feedback; production-scale readiness has not been established. Report bugs and request features through [GitHub Issues](https://github.com/ishantanu/nines/issues). The [release checklist](https://ishantanu.github.io/nines/docs/release/) records the checks required before publication.

## Login credentials

| How you started Nines | Default URL | Username | Web password |
| --- | --- | --- | --- |
| `go run ./cmd/server -demo` | [localhost:8080](http://127.0.0.1:8080) | `admin` | `admin` |
| `compose.playground.yaml` | [localhost:18080](http://127.0.0.1:18080) | `admin` | `admin`, unless you set `NINES_PLAYGROUND_PASSWORD` before first startup |
| `compose.yaml` | [localhost:8080](http://127.0.0.1:8080) | `admin` | Your `NINES_BOOTSTRAP_PASSWORD` value from `.env`; no fixed password |

**`POSTGRES_PASSWORD` is only for PostgreSQL. It is never the web-login password.** Both Compose configurations require it through `.env` or the shell environment; neither supplies a database default. API tokens are separate automation credentials.

For persistent Compose, open the private `.env` generated by `scripts/setup-local.py` to find `NINES_BOOTSTRAP_PASSWORD`. Existing volumes retain account passwords: editing a bootstrap variable does not reset a user. Change a known password under **Access control → Users**. The `admin` / `admin` credentials apply to the in-memory demo and loopback playground. Persistent Compose uses its configured password.

## Try the demo

Requires Go 1.27.3 or later. Node is not required to run the committed UI build.

```sh
go run ./cmd/server -demo
```

Open [localhost:8080](http://127.0.0.1:8080) and sign in with `admin` / `admin`. The demo uses synthetic data, isolated in-memory tenants and no external providers. The sample objectives include critical and warning burn policies. It resets on restart. Its sign-in is a demonstration, not a security boundary; keep it on loopback.

## Test Prometheus locally

Run the self-contained playground with Docker Compose. Set `POSTGRES_PASSWORD` in your shell or private `.env` first. On a fresh checkout, generate `.env` once with `python3 scripts/setup-local.py --playground`; it refuses to overwrite an existing file. Use a URL-safe database password.

```sh
# Fresh checkout only; skip if you already configured .env or POSTGRES_PASSWORD.
python3 scripts/setup-local.py --playground
docker compose -p nines-playground -f compose.playground.yaml up --build -d
# Allow several minutes for the complete integration check:
docker compose -p nines-playground -f compose.playground.yaml run --rm verify
```

Open [localhost:18080](http://127.0.0.1:18080) and sign in as `admin` with password `admin`. API-token access remains available with the local-only token `nines-local-playground-owner-token`. The **Playground Prometheus** workspace uses synthetic checkout metrics. Mimir is available through an [optional profile](https://ishantanu.github.io/nines/docs/deployment/playground/#optional-mimir-profile). The SLO detail shows separate saved, collected, deployed and evaluating states. Definitions and their rules are reconciled automatically in the playground. The verifier checks automatic deployment, exercises users/telemetry connections/RBAC, and checks critical/warning alert firing and recovery in Prometheus. See the [playground guide](https://ishantanu.github.io/nines/docs/deployment/playground/) for the complete flow and automated burn-alert/recovery test.

## Use the CLI without a server

```sh
make cli
bin/nines init slo --name checkout --window 28d --out checkout.yaml
bin/nines validate --offline -f checkout.yaml --agent
bin/nines rules generate --offline -f examples/api-availability.slo.yaml --tenant commerce
bin/nines capabilities --offline --agent
```

Create one SLO with its measurement, target, rolling window and alert policies together. The [guided SLO workflow](https://ishantanu.github.io/nines/docs/measurements/) generates queries from `spec.measurement`; no separate binding resource is needed. See [availability](examples/request-success.slo.yaml) and [latency](examples/request-latency.slo.yaml) YAML examples. Intents and the Kubernetes operator use the same inline contract.

Local validation checks the declared contract. It does not establish that a metric exists or that a measurement captures the intended user outcome. Recording-rule generation emits YAML without deploying it. `-f -` reads stdin; `--out` creates a new file without overwriting one.

## Run a persistent workspace

Requires Docker with Compose.

```sh
python3 scripts/setup-local.py
docker compose -p nines up --build -d
```

Compose binds the UI to localhost and stores PostgreSQL data in its own volume. Open [localhost:8080](http://127.0.0.1:8080) and sign in as `admin` using `NINES_BOOTSTRAP_PASSWORD` from the generated `.env`. Manage users under **Access control → Users**. API credentials remain available for automation. For a native server, supply `DATABASE_URL` and `API_TOKEN` through its environment; native execution does not automatically load `.env`.

Connect a CLI context to an authenticated deployment:

```sh
bin/nines config set-context production --server https://nines.example.com --tenant commerce
# Inject NINES_API_KEY through your shell or secret manager, or use configured SSO:
bin/nines login --context production --method sso
bin/nines get slos --context production --agent
bin/nines plan --context production -f reviewed.yaml --agent
bin/nines apply --context production -f reviewed.yaml --expected-revision 0 --agent
```

Compose enables local account login. OIDC SSO and LDAP use server-owned identity configuration. API-key login uses `NINES_API_KEY`, with `API_TOKEN` retained as an alias. Tenant membership and roles are checked by the server. See the [CLI guide](https://ishantanu.github.io/nines/docs/cli/).

## First-release scope

| Area | MVP scope |
| --- | --- |
| Definitions | SLOs, critical user journeys and explicit journey-step/SLO links in shared versioned YAML |
| Measurement | Event-ratio objectives, provider-window measurements, configurable rolling windows, budgets and up to eight named, severity-based two-window burn policies per SLO |
| Providers | Configured Prometheus/Mimir queries; server-owned tenant and rule destinations |
| Interface | Tenant-aware web workspace, charts, history, YAML review and revision-checked apply |
| Clients | Offline/connected Cobra CLI, typed Go client and stdio MCP adapter |
| Kubernetes operator | GitOps reconciliation, namespaced RBAC, lease-based standby, PrometheusRule/Mimir destinations and generation-scoped diagnostics |
| Identity | Local accounts, API/service-account keys, configured OIDC/LDAP, tenant roles and teams |

Reviewed intent updates refresh measurement quality and budget evidence at apply time. A durable observer then checks current rule activation/output and SLI evidence; regressions and uncertainty lead to a separate human rollback review. See [agent change safety and verification](https://ishantanu.github.io/nines/docs/intent-governance/#action-time-safety-checks).

Optional model-assisted intent/review workflows and session replay are **experimental**. They remain available for evaluation but are outside the initial supported deployment path. Models are optional and provider-configurable. No hosted LLM account is required. Run `make selection-eval` for template-selection contracts; use the [live acceptance guide](https://ishantanu.github.io/nines/docs/intent-evaluations/#template-selection-acceptance) to test your exact model before enabling it. See [experimental features and limits](https://ishantanu.github.io/nines/docs/experimental/).

Identity and tenant acceptance is reproducible with `make test-identity`, using disposable PostgreSQL, real OpenLDAP with LDAPS/StartTLS, signed OIDC fixtures and the native CLI. See the [identity acceptance guide](https://ishantanu.github.io/nines/docs/deployment/identity-acceptance/) for prerequisites and real-Entra verification limits.

## Development

Requires Go 1.27.3, Node 24, npm and Python 3.9 or later. Frontend and backend builds run in that order because Go embeds the generated web assets.

```sh
make ui
make build
make test
make check
make release-check
```

The development UI proxies to a Go API on `127.0.0.1:8189`. Run the server with that address when using `npm run dev --prefix web`. The [contribution guide](CONTRIBUTING.md) covers disposable PostgreSQL and Mimir integration checks.

Rule delivery follows the owner-configured source policy: automatic reconciliation after SLO saves, or a separate reviewed apply. Standalone Prometheus uses a shared rule directory and native reload; Mimir activates through its ruler; Kubernetes uses the Nines operator. File persistence, runtime evaluation and recorded output have separate status evidence. See [backend activation](https://ishantanu.github.io/nines/docs/deployment/metrics-and-rules/#automatic-backend-activation).

Portal SLOs can also deploy through the Kubernetes operator: configure an operator destination, review its resource plan and apply from the Rules tab or CLI. The operator reconciles provider rules and returns revision-scoped evidence. See [portal-to-operator setup](https://ishantanu.github.io/nines/docs/deployment/operator/#publish-portal-slos-through-the-operator).

Optional [System One advice with Jev](docs/public/system-one.md) adds typed template-category and definition-clarity judgments to intent preparation. It uses the native TypeSafe API, explicit tenant configuration and per-run consent; deterministic checks and human approval remain required.

The [platform admin console](docs/public/platform-administration.md) manages users, direct tenant grants, session revocation and Jev request limits. Open `/admin/tenants` after signing in with an explicitly configured platform administrator identity.
