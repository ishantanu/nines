---
name: nines-cli
description: Validate SLO and critical user journey YAML, generate recording rules offline, and use tenant-scoped Nines commands with explicit revision and digest checks.
---

Use the installed `nines` binary as the deterministic executor. No model inference is needed for validation, rule generation, revision checks or application. Discover supported operations with `nines capabilities --agent` and use leaf-command `--help` for input flags. Capability effects describe possible side effects, not authorization to perform them.

For local work, use `--offline`. `init slo`, `validate`, `rules generate`, and `operator crds|render` do not contact Nines or load credentials. These commands validate declared measurements; they cannot prove that telemetry exists or that the measurement captures a business outcome. Generated manifest/rule commands emit YAML even in agent mode; with `--out`, agent mode returns a JSON artifact receipt containing the created path, byte count and digest.

For connected work, select an explicit `--context NAME` or `--server URL --tenant ID`. Authenticate through `NINES_API_KEY` (or the legacy `API_TOKEN`) supplied by the caller, or a previously authenticated browser context. Never ask a model to read, print or paste a key. `--agent` never starts browser login. Use `nines auth status --agent` to verify the selected tenant and effective role before connected work.

Use `--agent` for JSON results and JSON errors on stderr. Successful data goes to stdout. Exit codes: 0 success; 1 local execution/validation failure; 2 invalid invocation; 3 unauthenticated/expired; 4 forbidden; 5 revision/digest/configuration conflict; 6 unavailable/timeout. Do not parse human tables. Canonical manifest exports remain YAML; `audit export` emits NDJSON, including in agent mode. Results that include timestamps, live telemetry or model output are not byte-reproducible.

Prefer one SLO with `spec.measurement` (or the same contract inside an intent); no separate binding resource is required. `telemetry verify -f slo.yaml` is a connected, read-only instrument check, while offline validation/rule generation remain model-free. A conversation confirmation pins `measurementDigest`, `intentDigest` and `expectedVersion`; only an owner/editor can confirm. Prepare exact YAML and review plans before authorized changes. `apply` requires `--expected-revision` (zero means create). Manual rule deployment requires the exact `--expected-digest` from `rules plan`. An owner-configured `rules.autoDeploy` source reconciles saved definitions automatically after commit; this does not grant approval authority. Owners can use `rules pause/resume --id SLO --expected-revision N` to control delivery without editing the SLO. Inspect `integration` automation/configuration/runtime evidence separately. For intent conversations, operational YAML pins `expectedVersion`, digest and confirmation; approve/apply only the exact reviewed change. Approval notes are mandatory and the approving subject cannot apply that change or rollback. Never create, acquire or substitute a second credential to bypass review separation; a separately authorized owner/editor must apply it. A changed definition, source, binding or conflict requires a fresh review. An agent role cannot confirm measurements, approve changes or deploy rules. Do not substitute an owner credential to bypass that boundary.

After a timeout on a write, inspect current revisions or the conversation apply receipt before retrying. Retry only with the same reviewed input and preconditions, within the user's authorized scope. Never weaken a target, broaden a population or change a destination to make validation pass. Record unknown health as unknown. Report rule acceptance separately from provider evaluation and SLO health. Use `nines integration SLO_ID --agent` to inspect definition, collection, rule deployment and external evaluation independently; this read performs no deployment or reload.

Use `nines audit list --agent` for owner/editor tenant-wide decision search, and `nines audit show RECORD_ID --agent` for its frozen proposal snapshot. `nines audit export --agent` streams all matching full records as NDJSON; check its exit code and never label a partial output complete. An `uncertain` apply outcome may mean the resource transaction committed before the response or journal persistence failed. Inspect readback and the exact durable receipt before retrying; do not claim no change occurred. Conversation audit JSON is paginated: follow `nextAfter` with the returned `through` snapshot. Exports are separate from external retention. `audit status --agent` reads owner/editor delivery receipts for an optional owner-configured S3 Object Lock archive. Pending/retrying does not mean archived; never configure destinations, acquire cloud credentials or extend retention without explicit owner authorization.
